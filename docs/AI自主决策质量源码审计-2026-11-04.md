## 2. 架构演进与当前有效代码路径

### 2.1 两条并行的上下文管线，只有一条真正生效

| 管线 | 入口 | 调用方 | 状态 |
|------|------|--------|------|
| 旧版 `Build(source)` | `DecisionContextCompression.cs:118-196` | 无任何调用方（全仓库 Grep 验证） | **死代码** |
| 新版 `BuildDecisionInput + Serialize` | `DecisionInput.cs:231-270` | `CompanionRuntime.Think()` — 唯一入口 | 活跃 |

旧版 `Build()` 包含 `greedyCandidates`、`projects`、`dailyPlan.goal` 等字段的完整注入逻辑（第 146-171 行），这些逻辑永远不会执行。新版通过 `trigger / playerGoal / agentState / world / decisionScope` 结构构造上下文，**没有任何等价注入**。

### 2.2 不可达的 execute_plan 分支

- `ModelClient.cs:193-228` 的 `ToolCatalog.Definitions()` **不定义**名为 `execute_plan` 的 tool。
- `CompanionRuntime.cs:386` 的 `name.StartsWith("group_",...)||name=="execute_plan"` 分支中 `name=="execute_plan"` 是永假条件。
- 实际批次执行入口是 `group_` 前缀的工具（`group_farming`、`group_business` 等）。

### 2.3 主决策触发链路

```
OnObserved(GameObservation)
  → 检测 session/day/location 变化
  → 设置 _triggerKind (session_started / new_day / task_terminal / no_action_retry / ...)
  → Run() 循环中 WakeDecision() 设置 _decisionRequested=1
  → Think(instruction)
    → AwarenessSnapshot() + ConversationSnapshot()
    → BuildDecisionInput(state, delivery, conversation, promptTools, instruction)
      → PlayerGoal / WorkState() / ScopeFor(tools) / ProjectWorld()
      → 对 _memory.Relevant() 只取 routine（project / agreement 被丢弃）
    → DecisionContextCompression.Serialize(context) 喂给 LLM
    → for round=0..2:
        → 模型选工具 → Runtime 执行 → 回执喂回模型 → 直到 mutation=true
        → 空决策 → 指数退避 5s→10s→20s→40s→80s
```

### 🔴 P-01：长期项目（projects）完全不进入 LLM 上下文

**严重程度：致命**

| 项 | 内容 |
|----|------|
| 代码文件 | `DecisionInput.cs:247-248`；`DecisionContextCompression.cs:163-171`（旧版死代码中的对应逻辑） |
| 实际执行路径 | `BuildDecisionInput` 调用 `_memory.Relevant()` 取得包含 `agreement`/`project`/`place`/`routine` 的记忆列表，随后用 `.Where(m => ...Text(m,"kind")=="routine")` **只保留 routine**。projects 被丢弃。旧版 `Build()` 中的 `result["projects"] = ...` 注入逻辑（第 163 行）是死代码。`MemoryStore.Projects()` 方法（第 144 行）存在且功能完整，但从未被决策主循环调用。 |
| 可复现场景 | 玩家在 Desktop UI 添加 3 个长期项目（"升级房屋"、"解锁温室"、"社区中心包"），启动自主游玩。观察 `Trace("decision_context",...)` 输出的 JSON：`relevantMemories` 数组只包含 routine 类型，无 project/agreement；整个 JSON 中不存在 `projects` 顶级字段。 |

| 最小修改方案 | 在 `BuildDecisionInput` 中：① `relevantMemories` 同时 include `project` 和 `agreement` kind（取 Top N by 相关度）；② 新增 `activeProjects` 字段，从 `_memory.Projects(_scope)` 拉取活跃项目数组，注入 `id / goal / nextStep / status / verifiedResults / lastCheckedSession` 结构化内容。不扩写 Prompt。 |

### 🔴 P-03：每日计划 goal 在换日时丢失

**严重程度：高**

| 项 | 内容 |
|----|------|
| 代码文件 | `DecisionInput.cs:90-94`（`RetireWorkingDay`）；`DecisionInput.cs:71-78`（`WorkState` 初始化）；`DecisionContextCompression.cs:154`（旧版死代码中的 `dailyPlan.goal`） |
| 实际执行路径 | 换日时 `OnObserved`（`CompanionRuntime.cs:95`）→ `RetireWorkingDay()` → 将 `agent_working_state.currentObjective / objectiveBasis / next / activePlanId` **全部清空**。上一天完成的计划 goal 不滚入下一天。`CompanionPlans.cs:104` 的 `_lastPlan` 在换日时被会话切换逻辑（`CompanionRuntime.cs:77`）置为 null，但换日是同一 session（`_memory.Reconcile` 仅针对 session 变化），所以 `_lastPlan` 在换日场景下不会被保留。 |
| 可复现场景 | Day 5 夜晚 LLM 创建 `group_farming` 计划（goal="春季第一批作物收获"）执行完毕 → `ExecutePlan` 正常返回 `status="completed"` → Day 6 凌晨换日 → 观察 `agentState.currentObjective` 为空字符串；`agentState.confirmedMilestones` 保留了 Day 5 的执行凭证，但 `currentObjective` 已丢失。 |

**严重程度：高**

| 项 | 内容 |
|----|------|
| 代码文件 | `CompanionRuntime.cs:425-442`（Think 中单独工具派发路径）vs `CompanionPlans.cs:79-80`（ExecutePlan 批次内的 `unchanged_target_previously_failed`） |
| 实际执行路径 | LLM 选择单独工具（如 `water_area`）→ Think → `BusinessExecutor` 派发。这条路径**没有** `FactFingerprint` + `_lastActionFingerprint` + `_unchangedFailures` 三重检测。批次执行（group_*/execute_plan）路径有三重防护，但批次外的单次调用完全裸奔。`DecisionAwareness.cs:56-72` 会往 blockers 数组累积记录，但这只是"提示 LLM 别再调"，不是程序强制。LLM 可能忽略。 |

### 🟠 P-05：blockers 的 LLM 可见性弱

**严重程度：中高**

| 项 | 内容 |
|----|------|
| 代码文件 | `DecisionAwareness.cs:56-72`（blockers 生成）；`DecisionInput.cs:239-240`（blocked phase 注入） |
| 实际执行路径 | blockers 被放在 `agentState.blocked` 数组。System Prompt 第 5 条说"遇到失败则判断原因、修正策略；不机械重试"，但没有内容说"agentState.blocked 里的条目是程序检测到的重复失败，必须先解决再重试"。LLM 把它当作普通反馈字段，权重不明。 |
| 可复现场景 | 商店关闭时尝试 `purchase_items` 失败 → blocker 记录 `key="purchase_items:...:shop_closed_for_day"`。下一轮 `BuildDecisionInput` 设置 `agentState.phase="blocked"`。但 LLM 可能仍然不知道"今天商店不开"这个事实，因为这不是结构化世界事实，只是 blocker 文本。 |
| 影响根因 | blockers 是"失败反馈"而非"世界事实"。某些 blocker（`shop_closed_for_day`、`inventory_full`）程序可以自动检测解除条件，但在解除前 LLM 可能反复触发。 |
| 最小修改方案 | 在 `BuildDecisionInput` 中，将 blockers 中可预测解除条件的条目提升到 `world.risks` 层级，作为结构化事实注入。例如：`{"shopClosedForDay": [{"location": "Town", "blockedDay": 5, "reopenDay": 6}]}`。不扩写 Prompt，只让程序保证 LLM 看到的是明确的世界状态。 |

### 🟠 P-06：Tool Schema 动态筛选过严 → 导致空决策

**严重程度：中**

| 项 | 内容 |
|----|------|
| 代码文件 | `DecisionInput.cs:184-218`（`DecisionTools`）；`CompanionRuntime.cs:478`（空决策指数退避） |
| 实际执行路径 | `DecisionTools` 基于 location + intent 字符串匹配缩小范围。默认 Farm 位置 + 无 farming 关键词时，暴露的 action 只有 `go_to/return_home/sleep/forage_area` 四个。玩家在 Town + 空 PlayerGoal.Objective 时，action 可能只剩 `go_to`。`DecisionInput.cs:214` 的 `!_expandedTools && !queries.Contains(name) && !TopLevelFrequentTools.Contains(name)` 过滤掉所有非顶级工具。 |
| 可复现场景 | Day 1 玩家刚进 Town 卖东西 + PlayerGoal.Objective 空（玩家没设置长期目标）。LLM 看到的 action 只有 `go_to/forage_area`。如果 Town 没 forage，LLM 可能返回空 → `empty_decision` → 重试 → 仍然空 → 指数退避最长 80 秒。 |

| 最小修改方案 | ① 加入 location-based 默认集：Farm → 默认 farming 全量；Town → 默认 commerce 相关；② 空 intent 时保留 TopLevelFrequentTools 全部 + 当前位置相关的 BusinessDomains。保留 `list_capabilities` 机制不变。 |
| 回归测试方案 | 构造 `Location=Farm + empty intent` → 验证 DecisionTools 包含 farming 全量；`Location=Town + empty intent` → 验证包含 commerce 工具。 |

### 🟡 P-08：wait_for_change 缺少结构化等待条件

**严重程度：中低**

| 项 | 内容 |
|----|------|
| 代码文件 | `CompanionRuntime.cs:397-406`；`ModelClient.cs:223-225` |
| 实际执行路径 | `wait_for_change` 接受 `seconds`（1-120）和 `reason` 纯文本。程序只做 seconds 范围校验，不校验 reason 是否对应可验证的条件变化。`FactFingerprint` 会被记录，`OnObserved` 里 `FactFingerprint(s)!=_waitFingerprint` 时解除等待。但 FactFingerprint 包含 inventory/soil/forage 等大量字段，任何微小变化（如玩家位置微变）都会打破等待。 |

## 5. 根因归纳

所有问题归结为**一条主线**：

> 2024→2025 期间进行了上下文管线重构（从 `DecisionContextCompression.Build(source)` 迁移到 `BuildDecisionInput`），但迁移不完整 — 旧管线被整体废弃，新管线没有对等地注入 `projects`、`greedyCandidates`、每日计划 goal，也没有为单独工具调用路径加失败防护。同时留下了若干死代码文件。

AI Agent 的五类症状均能追溯到这条主线：

| 症状 | 直接根因 | 对应问题 |
|------|----------|----------|
| **短视** | projects 完全缺失 + SeasonPlan 只在 agentState 内嵌套而非 top-level 字段 | P-01 + P-03 |
| **重复劳动** | 单独工具调用路径无失败防护 + LLM 被迫心算覆盖度 | P-04 + P-07 |
| **无效等待** | wait_for_change reason 无结构 + FactFingerprint 粒度过粗 | P-08 |
| **目标丢失** | 换日清空 currentObjective + Tool Schema 过严导致 LLM 无事可做 | P-03 + P-06 |
| **缺乏经营策略** | greedyCandidates 死代码 + blocking 提升为世界事实的机制缺失 | P-02 + P-05 |
